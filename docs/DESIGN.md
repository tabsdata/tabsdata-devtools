# tabsdata-devtools -- design

Dev tools in isolated environments behind one entry point, so tool dependencies never reach a
project's dependencies. This is the *why* and the mechanics that hold everything together; each
tool's own design is beside its code (index at the end). How-tos:
[building-a-python-command.md](building-a-python-command.md),
[building-a-shell-command.md](building-a-shell-command.md); the contract every command meets:
[command-cli-guidelines.md](command-cli-guidelines.md); install: the [README](../README.md).

## Three pieces

| | | |
|---|---|---|
| `tdd` | shell function, loaded from `<tdd_dir>/tdd-source.sh` or `tdd-source.ps1` | the front door; routes a word to whichever half owns it |
| `tdd-exe` | executable in `<tdd_dir>/tdd-venvs/tdd` | dispatches Python tools; `help`, `doctor`, `info`, `--reqs` |
| `tdd-fn` | shell function | commands that must change the calling shell (venvs, variables) |

`tdd-install` is the only way to build a tdd dir -- it breaks the bootstrap cycle (`tdd` cannot
exist before `tdd-source.sh` is written) and nobody wants envs rebuilt from inside a tool call.
Setup is `cargo make install` (`-- --editable` / `cargo make dev` links the checkout); the catalog
is regenerated by `cargo make gen`; tests run with `cargo make test`. None of those is a `tdd`
word. The build needs `uv` and `cargo-make`, nothing else; `uv` is a hard requirement and says
so: `uv is a hard requirement, install it`.

## The surface

```
tdd [--dir TDD_PATH] [--format json|view] [--verbose] <command> [args...]
```

`--dir` defaults to `$TDD_DIR`, then `~/.tdd`; everything after the word reaches the command
verbatim; `--format`/`--verbose` before the word also travel on to it. Commands: `venv`,
`tdd-env`, `env` (shell, marked `*` in `tdd help`), `system`, `domain`,
`xp`, `gsx`, `pycache`, `mexe`, `apidoc`, `tdk`, `tdkserver`, `km`, `pqt`, `jq`, `ci` (Python).
`tdd help` merges both halves from `tdd-exe --porcelain` and the shell registry.

**Command config**: `<tdd_dir>/<command>.toml`, one file per command, holding both what the
command keeps of its own and `[options]` -- what its options default to, `[options.<action>]` for
one action -- merged under what was typed, before a `--` when there is one (`tdd-exe --defaults`, stdlib,
unit-tested); `tdd` prints
the resolved line as `info`. Every command has a `config` action (`--show`, `--default`,
`--create [--force]`) built from its own options, so the template cannot drift; writes go through
a temporary file and one rename. It is user state: `tdd-install` never writes or removes it.

**Events everywhere**: one model on both sides -- `command` + `event` (`ok`, `error`, `warn`,
`info`, `debug`) + `message` + fields; json is one line per event, view puts `ok` on stdout and
the rest on stderr; exit 0/1; a failure log in `/tmp`. Shell commands get it from `common.sh`,
Python tools from `common.core.cli.run()`/`render`; `tdd-exe`, `tdd-install` and the generator
from `tabsdata_dev.tdd.render`, a byte-identical twin kept so by a test.

## Packages

All prefixed `tabsdata-dev-`, all under the PEP 420 namespace `tabsdata_dev` (no `__init__.py`
above the leaves), all laid out `src/python/main/` + `src/python/test/` with hatchling
`only-include` + `sources`.

| Package | Declares | Role |
|---|---|---|
| `-tdd` | nothing, stdlib | the executable, the installer, the generator |
| `-shell` | nothing | shell files as data |
| `-common-*` | third-party **ranges** | shared code; joins only toolsets whose tools use it (`common-core` all of them) |
| `-deps-*` | third-party **pins** (+ optional `[tool.tdd] python`) | a dependency bundle; its name is the toolset's |
| `-tool-*` | exactly one `-deps-*` + any `-common-*` | one tool; the `-deps-*` is what assigns its toolset |
| `-toolset-*` | its `-deps-*` + every tool using it | **generated**; its committed `uv.lock` is the env's record |

Arrows point opposite ways on purpose: tools depend on a bundle (so each is installable alone);
the toolset depends on the tools (so one sync materializes the env). **No uv workspace**: a
workspace forces one resolution, and two toolsets with conflicting pins must both exist --
two toolsets may pin the same package differently. `cargo make gen` warns when a shared
range resolved differently across locks (`cargo make lock` fixes it).

**Every lock resolves against PyPI alone** (`https://pypi.org/simple`). A lock records its
registry's URLs, and a developer's shell may point uv at a local mirror or a private index
(`UV_INDEX`, `UV_DEFAULT_INDEX`, ...); locked through one, a lock installs only where it runs,
and `uv sync` finds a PyPI lock "stale" against it and re-locks it there. So `cargo make lock`
and tdd-install's toolset sync both drop those settings and name PyPI, and the sync is
`--locked` -- an install never rewrites a lock, it fails naming `cargo make lock` (`--relock`
is the exception, and re-resolves against PyPI too). `test_discover` fails on a lock that names
any other registry.

## The catalog

`catalog.json` (generated, shipped inside `-tdd`, copied into the tdd dir as the "initialized"
marker) lists toolsets, `members` (every first-party dist per toolset -- wheels mode installs
`--no-deps`, which blocks first-party resolution too), tools (toolset, summary, `reqs`,
`hidden`/`launcher`; a `disabled` tool is not in it), shell commands (read statically, for `--reqs` and collision checks), the
interpreter map and a fingerprint. **Names only**: paths are composed at call time from the tdd
dir, so a dir is self-describing and relocatable.

## Dispatch

`tdd-exe` execs `<tdd_dir>/tdd-venvs/<toolset>/bin/<tool>` -- no activation, no `uv run` --
with the toolset's `bin/` first on `PATH` (a tool finds its pinned binaries) and `TDD_DIR`,
`_TDD_TOOL` exported (a tool reaches siblings through `proc.run_tool`, never an import). Before
exec it resolves every declared binary and refuses with the list of missing ones; `--help` is
never blocked. `tdd-fn` does the same for shell commands with `command -v`.

## External binaries

`bin-reqs.txt` -- one bare name per line -- at a Python tool's package root, beside a shell script
as `<file>.bin-reqs.txt` (`common.bin-reqs.txt` is folded into every shell command). `tdd --reqs`
reports `[ok]`/`[missing]` from the catalog against the ambient `PATH` (a pyenv/asdf/mise shim
counts only when its manager wires it); `cargo make check` fails on a missing one; `proc.run()`
refuses an undeclared, unpinned binary at the point of use. Everything else a tool needs is
carried by its package and found with `importlib.resources` -- never an OS path, the cwd or
`__file__` arithmetic: the same code runs editable, as a wheel, and in a relocated dir. A tree
that is *edited* rather than only read -- `tabsdata-dev-shell`'s scripts, `<repo>/smoke-tool/`,
`<repo>/xp-tool/` -- stays where it is edited and is `force-include`d into the wheel, which has
no effect on an editable install; those three locate both layouts, probing for a file they know.

## Environments

Every env is `uv venv --relocatable` with `UV_LINK_MODE=copy`, and `tdd-source.sh` locates
itself, so a tdd dir can be moved, copied or unzipped anywhere on the machine (not to another
machine: `bin/python` points at the uv-managed interpreter by absolute path; the `tdd-exe`
wrapper reports a dangling one plainly). Two install modes, one catalog: editable (links the
checkout; edits live; not relocatable) and wheels (`<dir>/wheels` + hashed exported locks; no
checkout needed). `cargo make install` evicts `tabsdata-dev-*` from the uv cache first -- uv
caches wheels by filename and the version does not change between builds.

`VERSION` at the repo root is the only version: every `pyproject.toml` is `dynamic` and reads
it; `-tdd` force-includes it; `tdd-install` stamps `<tdd_dir>/VERSION`, which `tdd --version`
prints.

## Host ports

Never ephemeral; the systems own 20000-29999 in fixed slots of 100 per type, everything else picks
from 30000-32767: [ports.md](ports.md).

## Variables

`TDD_*` is what a user sets or reads (`TDD_DIR`, `TDD_PARALLELISM`); `_TDD_*` is
private to the tool chain (`_TDD_TOOL`, `_TDD_VENV`/`_TDD_VENV_ACTIVATED`, `_TDD_COMMON_SH`, `_TDD_XP_SCRATCH`/`_TDD_XP_PARENT`,
`_TDD_CRYPTO_KEY`, `_TDD_SYSTEMS`) -- `tdd` warns off `_TDD_TOOL` found exported in a shell
(`_TDD_VENV` and `_TDD_COMMON_SH` live in the shell by design: `tdd venv` and `tdd-source.sh` put them there);
`TD_*` is tabsdata's own; a system's config is `<SYSTEM>__<KEY>`. `tdd env` manages them.

## Generator checks

One `deps-*` per tool; at least one entry point; no duplicate tool names, none equal to a
builtin or a shell command; every shell script registers a command; every `bin-reqs` line a bare
name with a script beside it; every toolset has its bundle; no lock drift. A tool marked
`[tool.tdd] disabled = true` is skipped before any of these: commented out, its package in
the tree and the generator blind to it.
